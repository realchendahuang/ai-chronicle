# AI Chronicle 技术栈规划

> 状态：2026-08-29 定稿。本文回答三个问题：为什么现在是静态站点、什么情况下必须引入动态、以及按什么顺序演进。

---

## 1. 为什么现在是静态站点（而且是对的）

当前架构：**Markdown 内容 → velite 解析 → 自研 SSG（scripts/ssg.mjs）→ 纯静态 HTML → Cloudflare Pages + 代理 Worker**。

这个选择不是"没得选"，而是当前阶段的最优解，理由有四条：

**1. 内容形态是"写时确定"的。**
249 个事件、478 篇文章、94 个概念——这些内容在构建时就已经完整存在，不需要在请求时计算。静态生成意味着每个页面都是预渲染好的 HTML，首屏零 JS 依赖、秒开、可被任何搜索引擎完整抓取。这是内容型产品能拿到的最好的性能与 SEO 起点。

**2. 成本趋近于零，且没有运维负担。**
Cloudflare Pages 免费额度对纯静态站绰绰有余。没有服务器、没有数据库、没有需要盯着的进程。对一个人维护的项目来说，"不会半夜挂掉"本身就是巨大的价值。

**3. 可靠性是内容产品的生命线。**
一个"编年史"产品，最不能接受的就是读者点开链接时 502。静态文件 + CDN 是可用性最高的部署形态。当前代理 Worker 的存在只是为了把 Pages 项目挂到主域名路径下，它不引入任何动态逻辑。

**4. 内容与代码同源，可审计、可回滚。**
每篇文章都是 git 里的一个 Markdown 文件。改一个字就是一次 commit，出问题可以精确回滚。这对"事实可核验"的编辑原则是结构性保障——动态数据库方案做不到这一点。

---

## 2. 静态站点的边界：什么做不了

静态站点不是万能的。以下需求它天然做不了，**当这些需求真实出现时**，才需要引入动态能力：

| 需求 | 为什么静态做不了 | 什么时候才需要 |
|------|------------------|----------------|
| 用户提交内容（贡献事件、纠错） | 需要写操作和存储 | 社区贡献机制上线时（规划书 §28） |
| 实时排行榜 | 数据每分钟在变，无法预渲染 | 永远不需要——我们做的是历史档案，不是实时榜单 |
| 个性化（登录、收藏、进度） | 需要用户态 | 有真实用户提出需求时 |
| 高频更新的动态数据 | 每次更新都要重新构建 | 排行榜快照是"每周一次"，构建完全来得及 |
| 站内搜索 | 需要索引和查询 | 已有方案：预生成 search-index.json + 前端检索，静态可解 |

**关键判断：排行榜历史图、评测档案、产业图谱——这三件新方向上的事，全部是静态可做的。** 排行榜历史图是"每周快照 + 构建时画图"，评测档案是"带版本戳的 Markdown 文章"，产业图谱是"结构化数据 + 静态可视化"。它们都不需要数据库。

---

## 3. 什么情况下必须引入动态（触发条件）

不要提前引入，但要知道触发条件。以下任一条件成立时，才值得讨论加动态层：

1. **用户生成内容上线**（规划书 §28 的贡献机制）——需要存储、审核流、写 API。
2. **访问量真实增长到需要登录态**——收藏、进度、个性化，需要用户系统。
3. **内容更新频率高到构建成为瓶颈**——当前构建是秒级到分钟级，每周更新一次内容远未触及瓶颈。
4. **需要服务端计算的交互**——比如"任意两个实体之间的关系路径"这类动态图查询。

即使到那时，正确做法也不是推翻静态：**静态为主、动态为辅**。内容页继续静态生成，只有需要写操作的部分（评论、提交、收藏）走动态 API。这是内容型产品的标准架构，也是成本最低的演进路径。

---

## 4. 演进路线（按顺序，不跳步）

```
阶段一（现在）：纯静态 + 代理 Worker
  内容：Markdown → velite → SSG → 静态 HTML
  新增：排行榜快照脚本（每周跑一次，产出 JSON + 历史曲线图）
       评测档案（带版本戳的 Markdown，走现有内容管线）
       分析埋点（Cloudflare Web Analytics，零成本）
  判断：这三件事全部静态可做，不需要任何架构变更

阶段二（当 UGC 需求真实出现时）：加一个轻量动态层
  方案：Cloudflare Workers + D1（SQLite）或 KV
  范围：只做"提交/审核/展示"的写路径，内容页保持静态
  判断：这是唯一值得考虑的动态引入点，且只覆盖 UGC 一个面

阶段三（当用户系统真实出现时）：再加认证
  方案：Workers 上的 OAuth（GitHub/Google）+ D1 存用户态
  判断：没有真实用户之前，不做

阶段四（当规模真实出现时）：再谈框架
  方案：Astro（内容优先，可渐进增强为岛屿架构）或 Next.js
  判断：当前自研 SSG 只有 2219 行，完全可控；换框架是"维护成本超过收益"时才做的事
```

**每个阶段都有明确的触发条件，没有一个是"现在就该做"。** 当前唯一正确的动作是：把阶段一里"新增"的三件事做掉。

---

## 5. 对"要不要换技术栈"的直接回答

**不换。** 当前技术栈（Markdown + velite + 自研 SSG + Pages）与产品形态是匹配的，换栈不会带来任何用户可感知的收益。真正缺的不是技术栈，是三个出口：搜索引擎收录、分析埋点、内容分发。这三件事与技术栈无关，做完它们，你才能知道"自嗨"是不是真的。

如果一定要给一个"未来值得关注"的候选，是 **Astro**——它保留静态生成的全部优势，同时提供岛屿架构，将来要加交互组件（排行榜历史图的交互版本、图谱的缩放拖拽）时，不需要推翻现有架构。但那是阶段四的事，现在不碰。
